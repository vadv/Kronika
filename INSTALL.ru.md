# Установить Kronika и записать свой Linux-хост

[English version](INSTALL.md) · [README](README.ru.md)

Kronika запускается двумя процессами: **collector** постоянно записывает
машину, **web** открывает её историю, когда она нужна. Начните с Linux.
PostgreSQL — дополнительный источник данных, а не хранилище самой Kronika.

В переносимом архиве пять статических программ для Linux: `kronika-collector`,
`kronika-web`, `kronika-dump`, `kronika-report` и `kronika-demo`. Для первых
четырёх не нужны Rust, Node.js, Docker или база данных. Demo запускает
искусственную нагрузку; для наблюдения своего хоста запускать его не нужно.

## 1. Скачать подходящий архив

**Опубликованный v1.0.0 старше этого руководства.** В нём нет `--version`,
`kronika-report`, `kronika-dump slice` и кнопки Export. До публикации нового
релиза скачайте артефакт workflow **Release package** для проверяемого
изменения. [Руководство по архивам](docs/releases.ru.md) описывает скачивание,
матрицу архитектур и проверки. Для скачивания артефактов Actions нужен вход
в учётную запись GitHub.

Если `uname -m` выводит `x86_64`, выберите `x86_64-unknown-linux-musl`; для
`aarch64` — отдельно собранный кандидат `aarch64-unknown-linux-musl`.
Используйте успешный запуск workflow для своей архитектуры. Это программы
Linux; архив не устанавливает ядро и не добавляет поддержку Windows или macOS.

Положите `.tar.gz` и соответствующий `.tar.gz.sha256` в новый каталог.
Ниже укажите **точное имя скачанного файла**. Контрольная сумма проверяет
соответствие выбранному артефакту; оба файла берите из одного доверенного запуска.

```sh
archive='kronika-1.0.0-REPLACE_WITH_COMMIT-x86_64-unknown-linux-musl.tar.gz'
sha256sum --check "$archive.sha256"
tar -xzf "$archive"
cd "${archive%.tar.gz}"
sha256sum --check SHA256SUMS
cat BUILDINFO
```

В `BUILDINFO` указаны ревизия упаковки и режим сборки. Имя кандидата содержит
commit, потому что версия исходного кода остаётся `1.0.0`: один вывод версии
не отличает этот кандидат от другой сборки той же версии. Сохраните `BUILDINFO`
вместе с архивом для сообщения об ошибке.

## 2. Проверить и установить программы

Из распакованного каталога, без `sudo` и настройки окружения:

```sh
for binary in kronika-collector kronika-web kronika-dump kronika-report kronika-demo; do
  "./$binary" --version
done
```

Каждая строка содержит имя программы и `1.0.0`, например
`kronika-collector 1.0.0`. Команды сразу завершаются, не запуская сбор,
сетевой сервер или демонстрационную нагрузку.

Установите пять программ в PATH:

```sh
sudo install -d -m 0755 /usr/local/bin
sudo install -m 0755 kronika-collector kronika-web kronika-dump \
  kronika-report kronika-demo /usr/local/bin/
/usr/local/bin/kronika-collector --version
```

Можно оставить программы в распакованном каталоге и использовать абсолютные
пути. Скачивать установочный скрипт и передавать его оболочке не требуется.

## 3. Записать Linux

На машине, которую хотите исследовать:

```sh
sudo install -d -m 0700 /var/lib/kronika
sudo env KRONIKA_STORAGE_DIR=/var/lib/kronika \
  /usr/local/bin/kronika-collector
```

Оставьте терминал открытым. Привилегии позволяют читать I/O процессов и
защищённые локальные журналы. Файлы коллектора закрыты для других пользователей;
запускайте web и dump с теми же привилегиями, не открывая запись всем.
Путь задан явно и должен быть настоящим каталогом, не symlink.

Основные метрики приходят примерно раз в 10 секунд, процессы — раз в 5 секунд;
у медленных инвентаризаций свои интервалы. Сбор начинается при запуске.
Web уже читает активный журнал: ждать стандартной 15-минутной записи сегмента
не нужно. `Ctrl+C` останавливает сбор и сохраняет журнал; повторный запуск
с тем же каталогом продолжает работу.

Цель retention по умолчанию — **2 GiB** для журналов, готовых сегментов и
индексов. Для фиксированного бюджета 10 GiB добавьте к команде коллектора
`KRONIKA_RETENTION=10737418240`. Перед выбором процента файловой системы или
оценкой числа дней прочитайте [правила хранения](bins/kronika-collector/README.ru.md).

## 4. Открыть запись

В другом терминале замените пароль из примера и запустите:

```sh
sudo env KRONIKA_STORAGE_DIR=/var/lib/kronika \
  KRONIKA_WEB_LISTEN=127.0.0.1:8080 \
  KRONIKA_WEB_SOURCES=1 \
  KRONIKA_WEB_USER=kronika \
  KRONIKA_WEB_PASSWORD='replace-with-a-random-password' \
  /usr/local/bin/kronika-web
```

Откройте **<http://127.0.0.1:8080/>**, войдите, выберите записанный час и
откройте Processes или Host. [Руководство оператора](docs/operator-guide.ru.md)
показывает, как найти занятый интервал, выбрать объект и проследить его историю.

Web нужен доступ на запись в тот же каталог для производных индексов и lock.
Он слушает loopback, аутентификация включена. Чтобы открыть удалённую машину
с рабочей станции, перенаправьте её локальный порт по SSH:

```sh
ssh -N -L 8080:127.0.0.1:8080 user@monitored-host
```

Затем откройте тот же localhost URL на рабочей станции. Если её порт 8080
занят, используйте `-L 8081:127.0.0.1:8080` и `http://127.0.0.1:8081/`.

MCP уже работает в этом процессе web по адресу
**`http://127.0.0.1:8080/mcp`**, с теми же учётными данными. Откройте панель
**AI** для настройки клиента или [руководство MCP](docs/mcp-clients.ru.md).
MCP извлекает записанные данные; он сам не подключается к работающему серверу
PostgreSQL и не читает текущее состояние хоста.

Для постоянного запуска и закрытых конфигурационных файлов есть
[руководство systemd](docs/services.ru.md). Команды выше подходят для первого
знакомства и временного исследования.

## 5. Подключить PostgreSQL при необходимости

На сервере PostgreSQL создайте отдельную роль наблюдения. В `psql` под
администратором пароль вводится по запросу и не попадает в текст SQL:

```sql
CREATE ROLE kronika_monitor LOGIN;
\password kronika_monitor
GRANT pg_monitor TO kronika_monitor;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_current_logfile() TO kronika_monitor;
```

Подключайтесь прямо к PostgreSQL или через **session pooling**. Сбор метрик
использует настройки сессии; transaction и statement pooling PgBouncer не
поддерживаются. Основные права, локальные права расширений и особенности
кластеров с ограниченным доступом описаны в [руководстве коллектора](bins/kronika-collector/README.ru.md).
Этой роли не нужны права на прикладные таблицы или superuser.

Остановите коллектор через `Ctrl+C` и перезапустите с тем же путём хранения
и своим DSN. Пример для PostgreSQL на той же машине:

```sh
sudo env KRONIKA_STORAGE_DIR=/var/lib/kronika \
  KRONIKA_PG_DSNS='host=127.0.0.1 port=5432 user=kronika_monitor password=replace-with-password dbname=postgres' \
  /usr/local/bin/kronika-collector
```

`KRONIKA_PG_DSNS` сам включает сбор метрик PostgreSQL. Первый DSN задаёт
сервер и его доступные базы; следующие DSN только обнаруживают журналы.
Отдельный DSN для каждой базы не нужен. Поддерживаемые установки
`pg_stat_statements` и `pg_store_plans` обнаруживаются автоматически;
установка расширений и изменение preload-настроек — отдельные операции DBA.
Activity, Locks, статистика баз и инвентаризация отношений не требуют
этих расширений.

Если эффективная ёмкость CPU наблюдаемого PostgreSQL известна, также задайте
`KRONIKA_POSTGRES_EFFECTIVE_CPUS` равным этому положительному целому числу. Kronika
использует его для PostgreSQL health и не выводит из числа CPU коллектора.
Без него метрики PostgreSQL доступны, но PostgreSQL health остаётся null.

Перезапустите web командой выше, заменив **`KRONIKA_WEB_SOURCES=1` на
`KRONIKA_WEB_SOURCES=3`**. Это объявляет OS и PostgreSQL настроенными;
переменная не запускает сбор и не фильтрует сохранённые данные.

Пути из log discovery должны быть доступны **на машине коллектора**. Для
смонтированных удалённых журналов задайте `KRONIKA_PG_LOGS`; для журналов
PgBouncer — `KRONIKA_PGBOUNCER_DSNS` или `KRONIKA_PGBOUNCER_LOGS`. Права,
форматы журналов и интервалы перечислены в руководстве коллектора.
Нативный клиент PostgreSQL сейчас использует `NoTls`: выбирайте локальное
соединение или защищённый транспорт; один DSN не включает TLS.

Для сервисов храните DSN и пароли web в закрытых файлах окружения из
[руководства systemd](docs/services.ru.md), а не в истории команд.
