# Архивы релизов

[English version](releases.md) · [README](../README.ru.md)

## Текущий опубликованный архив

[v1.0.0](https://github.com/vadv/Kronika/releases/tag/v1.0.0) — статический
архив для Linux x86-64 с musl. Внутри верхнего каталога лежат
`kronika-collector`, `kronika-web`, `kronika-dump` и `kronika-demo`.
**В этой версии ещё нет `kronika-dump slice`, `kronika-report` и
HTML-экспорта.** Для текущих возможностей используйте
[сборку из исходного кода](../README.ru.md#собрать-актуальные-бинарные-файлы).

Эти ссылки скачивают существующий релиз, а не будущую упаковку:

```sh
curl --fail --location --remote-name \
  https://github.com/vadv/Kronika/releases/download/v1.0.0/kronika-1.0.0-x86_64-unknown-linux-musl.tar.gz
curl --fail --location --remote-name \
  https://github.com/vadv/Kronika/releases/download/v1.0.0/SHA256SUMS
sha256sum --check SHA256SUMS
tar -xzf kronika-1.0.0-x86_64-unknown-linux-musl.tar.gz
cd kronika-1.0.0-x86_64-unknown-linux-musl
```

Для этой версии пользуйтесь инструкциями внутри её архива. Опубликованного
архива для arm64 нет. Docker-демо собирается из исходного кода на amd64 и arm64.

## Подготовить текущую упаковку

Запустите из чистого checkout на Linux x86-64 с закреплённым Rust toolchain, target
musl, `musl-gcc`, GNU tar, gzip, binutils и Python 3.11 или новее:

```sh
scripts/package-release.sh
```

Скрипт собирает release-версии **collector, web, dump и report** с locked
зависимостями, проверяет, что каждый файл — статический x86-64 ELF, и создаёт:

```text
dist/kronika-<cargo-version>-<12-character-commit>-x86_64-unknown-linux-musl.tar.gz
dist/kronika-<cargo-version>-<12-character-commit>-x86_64-unknown-linux-musl.tar.gz.sha256
```

Добавьте `--with-demo`, чтобы включить `kronika-demo`, как в CI. Бинарные файлы
лежат прямо внутри одного верхнего каталога рядом с `LICENSE`, парными README
и INSTALL, связанными руководствами, иллюстрациями и редактируемыми исходниками
схем, `THIRD_PARTY_LICENSES.html`, лицензиями шрифтов, `BUILDINFO` и `SHA256SUMS`
для всех файлов пакета. Иллюстрации берутся из commit упаковки. Ссылки между
вложенными руководствами остаются локальными; ссылки на исходный код открывают
этот commit на GitHub. Инструкции по установке используют относительные пути
к бинарным файлам. Деревья исходного кода и сборки, записи нагрузки и сведения
о машине не копируются.

Уведомления о лицензиях относятся к закреплённым зависимостям Rust и браузерного
интерфейса. Упаковка проверяет хеши входных файлов в
`licenses/dependency-inputs.sha256`; при изменении зависимостей обновляйте
уведомления и хеши вместе.

Чтобы упаковать уже собранные из этого checkout файлы:

```sh
scripts/package-release.sh \
  --bin-dir target/x86_64-unknown-linux-musl/release \
  --output-dir dist
```

`--bin-dir` пропускает компиляцию: вызывающий передаёт файлы, собранные из
нужной ревизии. В `BUILDINFO` записываются `build_mode=prebuilt` и commit
checkout, из которого выполнялась упаковка; ревизия самих бинарных файлов не
угадывается. По умолчанию скрипт собирает из исходного кода и записывает
`build_mode=source`, команду Cargo и версию компилятора. В режиме prebuilt
компилятор и команда сборки не записываются.

Упаковка фиксирует порядок, права, владельца и группу, время файлов (Unix-время
commit) и метаданные gzip. Одинаковые бинарные файлы, документация, иллюстрации, лицензии,
ревизия и режим сборки дают одинаковый архив. Это не обещание побайтово
одинакового результата независимых компиляций. Существующий архив или checksum
не перезаписывается; для повторной упаковки укажите новый выходной каталог.
Скрипт отказывается работать с незакоммиченными изменениями checkout и не
меняет версию, теги или релизы.

## Проверить подготовленный архив

При установленных Node.js 22 и Chromium или Google Chrome:

```sh
scripts/check-release.sh dist/*.tar.gz
```

Передайте ровно один архив. Проверка сверяет checksum архива и всех его файлов,
статические ELF, вложенные руководства, иллюстрации и локальные ссылки.
Она распаковывает пакет во временный каталог, проверяет отказ коллектора при отсутствии
обязательной настройки, затем запускает dump, срез по времени, детерминированную
генерацию отчёта, web-каталог с аутентификацией и получение списка MCP-инструментов.
Существующая браузерная проверка открывает HTML прямо с диска и проверяет
интерактивное чтение данных и отсутствие внешних запросов. Временные файлы и
локальный web-процесс убираются при выходе. PostgreSQL и локальный запуск BDD
не нужны.

[Workflow Release package](../.github/workflows/release-package.yml) запускается
для pull requests и вручную. Он собирает все пять исполняемых файлов, выполняет
эти проверки, побайтово сравнивает повторные упаковки и загружает архив с
checksum в GitHub Actions artifact со сроком хранения 14 дней. У workflow
только `contents: read`, в нём нет создания тегов или публикации релиза.
Версия Cargo не меняется; артефакты с commit в имени предназначены для проверки.
