# kronika-collector

[English version](README.md)

`kronika-collector` читает метрики операционной системы и PostgreSQL, следит за
логами PostgreSQL и PgBouncer и записывает сегменты Kronika. Публичного
интерфейса командной строки нет; коллектор настраивается переменными окружения.

## Настройка

До первого сбора демон один раз читает и разбирает все переменные ниже. Если
значение не удаётся разобрать, демон останавливается и сообщает имя переменной
и неверное значение. Значение по умолчанию не подставляется.

Число строк от одного источника не ограничено. Обычный снимок держит все строки
источника. Большие результаты PostgreSQL читаются пакетами ограниченного
размера без отбрасывания строк. Каждая запись `segment_write_finish` в логе
содержит `rss_kib` — пиковый размер резидентной памяти процесса.

Обязательна только переменная `KRONIKA_OUT_DIR`.

### Хранилище

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `KRONIKA_OUT_DIR` | — | Корень данных: журнал, готовые сегменты и блокировка записи. |
| `KRONIKA_SEGMENT_MAX_BYTES` | 64 MiB | Записать открытый сегмент, когда журнал накопит столько необработанных байтов. |
| `KRONIKA_SEGMENT_MAX_AGE_S` | 900 | Записать открытый сегмент по истечении этого времени, даже если предел байтов не достигнут. |
| `KRONIKA_JOURNAL_MAX_BYTES` | 1 GiB | Жёсткий предел `active.wal`. При его достижении открытый сегмент записывается досрочно, а добавление не завершается с ошибкой. |
| `KRONIKA_RETENTION` | 2 GiB | Целевой размер всего дерева для ротации: бюджет в байтах, `auto` (= `auto:80`) или `auto:P` для целевой доли занятого места на разделе, где хранятся данные. |

### Интервалы сбора

Планировщик отслеживает интервал каждого источника отдельно. Он ждёт не более
`KRONIKA_INTERVAL_S` и возобновляет работу раньше, когда наступает время опроса
источника. При интервале `0` источник читается в каждом цикле таймера.

| Переменная | По умолчанию, с | Секции |
| --- | ---: | --- |
| `KRONIKA_INTERVAL_S` | 5 | Максимальное время сна таймера; `0` отключает таймер, и сбор запускают только сигналы. |
| `KRONIKA_OS_CORE_INTERVAL_S` | 10 | `1_102`–`1_111`, `1_114`–`1_120`. |
| `KRONIKA_OS_MOUNTTOPO_INTERVAL_S` | 60 | `1_112`, `1_113`. |
| `KRONIKA_OS_PROCESS_INTERVAL_S` | 5 | `1_100`. |
| `KRONIKA_OS_PROCESS_STATUS_INTERVAL_S` | 30 | `1_101`. |
| `KRONIKA_OS_CGROUP_INTERVAL_S` | 10 | `1_201`–`1_204`. |
| `KRONIKA_OS_CGROUP_MAPPING_INTERVAL_S` | 30 | `1_200`. |
| `KRONIKA_LOG_INTERVAL_S` | 10 | `2_001`–`2_007`, `2_100`. |
| `KRONIKA_PG_INTERVAL_S` | 30 | `1_001`–`1_012`, `1_015`–`1_017`, `1_019`. |
| `KRONIKA_PG_RELATIONS_INTERVAL_S` | 300 | `1_013`, `1_014`; поиск баз и расширений. |

### С какого сервера собирать метрики

Секции с метриками `PostgreSQL` собираются с сервера, указанного первым в
`KRONIKA_PG_DSNS`. В строке метрик нет столбца с именем сервера-источника.
Поэтому по остальным DSN коллектор читает только логи, а при запуске с
несколькими DSN пишет в лог одну строку о том, какой сервер выбран.

Статистика по таблицам и индексам доступна только в базе данных, которая её
сформировала. Коллектор держит по одному соединению с каждой доступной для
подключения базой и использует его не более часа, пока оно исправно.
Пятиминутный проход обнаружения открывает соединение с появившейся базой и
закрывает соединение с удалённой. Исправное соединение закрывается и открывается
заново по достижении одного часа, чтобы ограничить ресурсы соединений
коллектора, память backend PostgreSQL и ресурсы сессии. Ошибка подключения,
протокола или клиентского тайм-аута запроса также заставляет следующий сбор
подключиться заново.

Расширения устанавливаются отдельно в каждой базе, даже если их статистика
относится ко всему инстансу. Во время того же прохода коллектор выполняет по
одному компактному запросу инвентаризации в каждой базе и кэширует базу, схему
и доступные интерфейсы каждой установки. Для каждого расширения выбирается одна
пригодная установка, поэтому общие строки не дублируются. Создание, удаление или
перенос расширения меняет выбранную установку при следующем проходе.

`pg_stat_statements` собирается начиная с версии расширения 1.5; каждому набору
столбцов соответствует свой формат. Вариант `pg_store_plans` определяется по
интерфейсу функций и столбцам результата, а не по `extversion`. Для функций без
аргументов у OSSC и Datasentinel используются разные форматы; также коллектор
распознаёт интерфейс vadv с булевым аргументом и функцией получения плана по
четырём ключам. Коллектор находит доступные представления
`pg_stat_statements_info` и
`pg_store_plans_info` с точной ожидаемой схемой. Каждое представление info
выбирается независимо от основной функции чтения статистики. Полная таблица
форматов приведена в
[справочнике метрик PostgreSQL](../../docs/type-registry/postgresql-metrics.ru.md).
Если в разных базах доступны разные форматы, коллектор выбирает самый новый
формат `pg_stat_statements`. Реализации `pg_store_plans` не ранжируются: при
наличии подходящего интерфейса выбирается текущая база, иначе выбор однозначно
определяет имя базы.

`pg_settings` читается при каждом сборе PostgreSQL. Полный снимок записывается
после первого успешного чтения, при изменении настройки и в каждый новый
сегмент. Если между сборами PostgreSQL сегмент открывают метрики ОС или строки
логов, коллектор использует последний успешный снимок.
Строки `primary_conninfo` и `ssl_passphrase_command` не сохраняются: их значения
могут содержать секреты. Остальные командные настройки, включая
`archive_command` и `restore_command`, а также пользовательские настройки
сохраняются.

### Выполнение запросов к PostgreSQL

Небольшие служебные запросы используют Simple Query Protocol PostgreSQL.
Типизированные запросы метрик выполняются один раз через безымянный Extended
Protocol. В каждом соединении запросы идут последовательно: коллектор не создаёт
именованных prepared statements и не использует pipelining.
Все постоянные соединения одного процесса коллектора используют одно уникальное
значение `application_name`; строки activity и locks исключают именно его.

Перед выдачей каждой новой frontend-сессии PostgreSQL коллектор отправляет ровно
один Simple Protocol запрос `SET statement_timeout = '30s'` и ждёт его
завершения. Этот серверный предел служит основной защитой запроса. Клиентский
предел чтения в Rust равен 35 секундам и остаётся аварийной защитой от зависания
сети или протокола; после его истечения коллектор выполняет одну ограниченную
попытку CancelRequest и закрывает соединение.

DSN метрик PostgreSQL поддерживают прямое подключение к PostgreSQL и PgBouncer в
режиме session pooling. Режимы transaction и statement pooling PgBouncer для
сбора метрик не поддерживаются, потому что они не сохраняют состояние сессии
`SET`/`RESET` между запросами. Коллектор не добавляет startup `options` и не
создаёт отдельную транзакцию для каждого запроса ради имитации состояния сессии.
`KRONIKA_PGBOUNCER_DSNS` использует отдельный путь к административной консоли
PgBouncer и не получает PostgreSQL session `SET`.

Потенциально большие результаты читаются пакетами не более 256 строк с целевым
размером около 512 KiB декодированных прикладных данных. Последняя ограниченная
в SQL строка может превысить этот целевой размер. Каждый пакет кодируется и
добавляется в WAL до чтения следующей строки. Отбора top-N и общего бюджета
текста планов нет. Текст каждого запроса или плана ограничивается в SQL первыми
65 536 символами до передачи по соединению.

Если поток завершается с ошибкой после добавления предыдущих пакетов в WAL, эти
пакеты остаются на месте. Коллектор записывает ошибку в лог, прекращает текущее
чтение и переходит к независимым источникам. SQLSTATE PostgreSQL `57014` от
`statement_timeout` учитывается как тайм-аут запроса; после ответа PostgreSQL
`ReadyForQuery` сессия остаётся пригодной для повторного использования.
Клиентский аварийный тайм-аут закрывает соединение, а ограниченная попытка
CancelRequest имеет предел в одну секунду.

Для каждого мониторингового SQL-запроса на уровне debug записывается событие
`pg_query_finish` с длительностями и счётчиками. Чтение дольше 500 ms также
создаёт предупреждение `pg_query_slow`. Примерно раз в пять минут и при
завершении процесса `pg_query_summary` сообщает число и частоту запросов,
строки, оценку логических прикладных байтов в обоих направлениях, ошибки,
тайм-ауты, медленные запросы, время чтения, кодирования и добавления в WAL,
размер кодированных и записанных данных и `peak_rss_kib`. В логе соединение
обозначается как `user@host:port`; исходный DSN туда не попадает.

### Какие логи читать

Источник задаётся одним из двух способов. Если задан DSN, сервер сообщает,
какой файл и в каком формате он пишет и как его идентифицировать. Если задан
путь или glob-шаблон, коллектор читает файл без сведений о его создателе. Можно
использовать оба способа одновременно; файл, найденный обоими способами,
читается один раз и получает сведения от сервера.

Каждая переменная содержит список, разделённый `;`. Так можно перечислить
несколько кластеров или пулеров на одной машине. Если не задана ни одна из
четырёх переменных, логи не читаются.

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `KRONIKA_PG_DSNS` | не задано | Соединения для метрик и обнаружения логов PostgreSQL. Каждая запись даёт расположение и формат лога; строки метрик поступают только от первой. |
| `KRONIKA_POSTGRES_EFFECTIVE_CPUS` | не задано | Положительная эффективная ёмкость CPU первой цели метрик PostgreSQL. Нужна для числового состояния PostgreSQL и никогда не выводится из CPU машины коллектора. |
| `KRONIKA_PG_LOGS` | не задано | Явно заданные логи PostgreSQL. Запись со `*` или `?` в последней части пути — шаблон для этого каталога. |
| `KRONIKA_PGBOUNCER_DSNS` | не задано | Соединения с PgBouncer для `SHOW CONFIG`, где указан `logfile`. Учётная запись должна входить в `stats_users`; другие административные права не нужны. |
| `KRONIKA_PGBOUNCER_LOGS` | не задано | Явно заданные пути и шаблоны логов PgBouncer. |

Размер логов задаёт другая программа, поэтому коллектор читает их через буфер
4 MiB и не держит файл целиком. За один сбор из каждого файла читается не более
256 MiB.

Все случаи отсутствия источника обрабатываются одинаково: сервер недоступен,
`logging_collector` выключен, `logfile` не задан, файл ещё не создан или появился
новый инстанс. Коллектор пишет одну строку в лог и через пять минут заново
определяет полный набор. Сбор системных метрик при этом продолжается. При каждом
проходе обновляются путь, формат и `log_line_prefix`. `system_identifier`
запрашивается до первого успешного результата и затем хранится до завершения
процесса.

DSN может указывать на сервер на другой машине, и полученного пути не будет в
локальной файловой системе. В логе появятся путь и подсказка: смонтировать
каталог и указать файл в `KRONIKA_PG_LOGS`.

Состав строки зависит от способа задания источника. Для источника с DSN строка
PostgreSQL содержит `system_identifier`, который сохраняется при перезапусках и
переименованиях. Для явно заданного пути это поле равно `null`; формат
определяется по первой записи. Префикс `stderr` разобрать нельзя, поэтому такая
запись сохраняет только время и текст. Каждая строка содержит путь к исходному
файлу.

### Другие параметры

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `KRONIKA_LOG_LEVEL` | `info` | Одно из значений: `error`, `warn`, `info`, `debug`, `trace`. |
| `KRONIKA_PROC_ROOT` | `/proc` | Точка монтирования procfs. При другом пути обнаружение контейнера также ограничивается cgroup-файлом под этим корнем. |
| `KRONIKA_SYS_ROOT` | `/sys` | Точка монтирования sysfs. |
| `KRONIKA_STATVFS_FIXTURE` | не задано | Параметр для тестов: использовать значения ёмкости `path=TOTAL:FREE;...` вместо вызова `statvfs`. |

Ёмкость файловой системы запрашивается только для `ext2`, `ext3`, `ext4`, `xfs`,
`btrfs`, `f2fs`, `zfs`, `tmpfs` и `overlay`. Для сетевых, FUSE/userspace,
`autofs` и неизвестных типов файловых систем поля ёмкости остаются без
значений. Один вспомогательный процесс обрабатывает все разрешённые точки
монтирования с общим тайм-аутом в одну секунду, поэтому заблокированный запрос
ёмкости не останавливает последующие снимки.

## Запуск коллектора

```sh
KRONIKA_OUT_DIR=/var/lib/kronika kronika-collector
```

`SIGTERM` и `SIGINT` останавливают цикл и оставляют журнал на месте, чтобы после
перезапуска восстановить собранные данные. `SIGUSR2` немедленно собирает одно
окно, не дожидаясь следующего срабатывания таймера.
